## 做了什么

`HANDOVER.md` 第五节列的第 1 条未验证项是"多会话真并行没验过"。它有两半：**机制**（迟到加入者能不能拿到队友的结论）和**画面**（三个窗格能不能同时跑）。这一轮把**机制**那一半用确定性测试验掉了，画面那一半交给 Lane B 第 10 轮。

为什么机制这半更要紧：整个"1 加到 3 省时间"的主张，全押在**第 2、3 个会话拿到的是蒸馏后的状态**上。如果简报漏了队友的死路/意图/租约，后加入的会话就会重做第 1 个已经做完的事——那省时间就是假的。

M1 只验过"两会话的死路继承"。这次补的是三会话 + 意图 + 租约 + 自我排除 + 崩溃继承。

## 没做什么 / 已知问题

1. **这是确定性测试，不是真并行。** 它证明的是"机制正确"，不证明"三个真实 agent 同时跑不会互相干扰"。后者要 Lane B 的画面证据 + 一次真的三会话运行。
2. **没有测黑板写入的并发。** 三个会话同时 `submit_fact` 会不会撞写锁？主进程串行队列的设计上应该没问题，但没实测。
3. **`in_flight` 只列 `status='claimed'` 的意图。** 如果某个会话登记了意图但一直没做（僵住），它会永久占着 `do_not` 里的一行。没有超时回收。
4. **租约过期回收没在这里测。** `acquireLease` 有过期逻辑（§8.6），但"会话崩了租约立刻释放"是 M1 验的，这里只验了"简报能看到租约"。
5. **简报只发一次（首条 prompt）。** §7.4 的设计是靠 agent 之后自己 `read_since` 拉增量。这是刻意的（不打断推理），但意味着**简报一旦漏了信息，那一整个会话就不知道**——除非它自己按纪律去拉。
