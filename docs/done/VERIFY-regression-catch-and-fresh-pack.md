# 回归抓到一个自引入的 bug + 发现 dist/ 是旧的（已重打）

> 完成时间：2026-10-13 09:42

## 做了什么

两件事，都是"跑一遍才发现"。

### 1. 回归抓到我自己引入的 bug：`verify:gate-live` 从 16/16 掉到 12/16

我为了给假 agent 加"重复发同一个请求"的能力（`FAKE_REPEAT`），改了它写回结果文件的**结构**——从"原始应答消息"包成了 `{ last: msg, answered, sent, repeat }`。但 `verify-gate-live.ts` 是直接读 `resp.result.outcome` 的，包一层之后就读不到了，于是三条断言全灭。

修法：**保留原始应答结构**（顶层仍是 `jsonrpc/id/result`），把计数器挂上去：`{ ...msg, answered, sent, repeat }`。回到 16/16。

这条值得单独记的原因：**它是我自己引入的、而且只有把回归跑起来才会暴露**。写完就直接改下一个东西的话，它会一直躺在那里——而它破坏的正是"三种结局都验过"这个结论。

### 2. `dist/` 是旧产物，不含 L-4 与退避签名的修复

`dist/` 里的安装包与绿色包是 **08:24** 打的，而 L-4 修复在 **08:42**、退避签名修复在 **08:44**。也就是说：**发给队友的两个产物里没有这两个修复**。

重打后 `dist/` 为 09:40，并复验：`11/11`（打包态），图标警告仍无。

这条的教训比上一条更值钱：**打了包之后又改了主进程代码，产物就静默过期了**，而没有任何机制提醒你。这属于"靠人记得"的环节——本轮靠的是"顺手看一眼 mtime"，不是机制。

## 没做什么 / 已知问题

1. **`dist/` 过期这件事没有机制防护。** 现在靠"记得重打"。可考虑：把 git 提交或某个脚本在打包后记一个 hash，启动时对比；或者干脆把 `pack` 放进"改完主进程就该跑"的清单里。**本轮没做**。
2. **打包产物里 L-4 修复的"存在"还没被直接验证。** 我只验了打包态 `--verify` 11/11，而那个自检**不覆盖 UI 拒绝链**。已派 Lane B 第 21 轮把它那个 ui-deny 脚本改造成可指向打包 exe，去证"修复确实随包发出了"。
3. **回归套件本身也有"覆盖盲区"。** 这次是 `verify:gate-live` 抓到的，但如果我改的是别的东西、而它只影响某个没进回归的路径（比如只有真实 agent 才走的路径），跑回归也不会亮红灯。本夜已经吃过两次（L-3、L-4 都只有真实路径才暴露）。
4. **四个套件加起来 100 条断言，但没有一个总入口。** 现在是一条条手动跑。建议加 `npm run verify:all`（本轮没做，因为要动 package.json 的脚本编排，留给你定）。

## 下一手需要什么

- 第 4 条很便宜：加一个 `verify:all` 把四个确定性套件串起来，避免"以为跑了其实漏了一个"。
- 第 1 条若要防护，需要设计（打包产物记 hash + 启动对比），不是十分钟的事。
