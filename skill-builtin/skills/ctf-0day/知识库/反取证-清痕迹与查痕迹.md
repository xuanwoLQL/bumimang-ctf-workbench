# 反取证：清痕迹 ↔ 查痕迹对位表

> **用途**：应急题里，"痕迹被清掉"是最常见的卡点。本表把**攻方怎么清**和**守方怎么查**做成两列对位 ——
> 看到"日志被清/查不到证据"，直接查右列；反过来，做攻防题要藏痕迹时看左列。
> **纪律**：左列是**对抗研究/防守演练用**；比赛里用来**判断"对手清了什么→我该去哪找残留"**。
> 来源标注：**实测** = 本地或靶场验证过；**素材** = 来自公开攻防资料（未本地验证，但为业界公认手法）。

---

## 一、Windows：日志与卷影

| 攻方：怎么清 | 守方：怎么查（及为什么还能查到） |
|---|---|
| `wevtutil cl System` / `clearev`（Meterpreter）清事件日志 | ① **先看日志文件本身**：`C:\Windows\System32\winevt\Logs\*.evtx` **大小为 0 或异常小** = 被清；② **看 1102 事件**（"审计日志被清除"）—— **清日志这个动作本身会记一条 1102**（很多攻击者忘了删它）；③ 内存里的 `Security.evtx` **往往未被清**（见下"内存留存") |
| `vssadmin delete shadows /all /quiet` 删卷影 | ① `vssadmin list shadows`（若还能列出说明没清干净）；② **查它的执行痕迹**：Prefetch / Amcache / 命令行审计（4688）/ Powershell 4104；③ 卷影被删 ≠ 文件不可恢复：**用 `photorec`/`testdisk` 或磁盘镜像里做文件雕刻** |
| 删 USN Journal（清文件操作记录）<br>`fsutil usn deletejournal /d c:` | ① `fsutil usn queryjournal C:` —— **Journal ID / First USN 异常** = 被清过户；② **清完到再次启用的窗口内的文件操作没有记录**，但 **$MFT 的 `$STANDARD_INFORMATION` 与 `$FILE_NAME` 时间戳还在**（换查 MFT）；③ USN 被清**本身**可能留在日志里（若开了审计） |
| 直接删文件 | ① **`$MFT` 里仍有残留记录**（文件名 + 时间戳），用 `MFTECmd` / `analyzeMFT` 解析；② 小文件内容可能仍在磁盘未覆写区 ⇒ **`photorec` 恢复**；③ 若进程仍持有句柄 ⇒ **`Get-Process` + `handle.exe` 找"已删除但仍打开"的文件**（**实测有效**：Linux 上对应 `/proc/<pid>/fd` 里的 `(deleted)`） |

## 二、Windows：ETW / 遥测（**这是"查不到日志"的根因之一**）

| 攻方：怎么清 | 守方：怎么查 |
|---|---|
| **ETW 补丁**：把 `EtwEventWrite` 的首字节改成 `0xC3`（`ret`）⇒ **本进程后续的 ETW 事件全部不上报**（.NET 系工具的经典免杀） | ① **内存取证**：dump 进程后检查 `ntdll.dll!EtwEventWrite` 的首字节**是不是 `0xC3`**（正常应是 `4C 8B DC` 之类序言）—— **实测判据**；② 只在**被 patch 的进程内**失效，**系统级 ETW（如 Sysmon 内核侧）不受影响** ⇒ 先确认有没有 Sysmon/EDR 在收 |
| 卸载/停用 Sysmon：`sc stop Sysmon` / `fltmc unload SysmonDrv` | ① **服务状态变更**（7045/7036 事件）；② Sysmon 自己的日志**在停用时刻截断**——截断点就是攻击时刻 |
| 关掉 PowerShell 脚本块日志（改注册表） | ① 注册表项 `HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging` 的**修改时间**；② 已记录的历史 4104 仍在（**改注册表不能删已有日志**） |
| **AMSI 绕过**（改 `AmsiScanBuffer` 返回值/首字节） | ① 内存里查 `amsi.dll!AmsiScanBuffer` 是否被改（同 ETW 的查法）；② **AMSI 事件日志**（若开了 `Microsoft-Windows-AMSI`）在 patch **之前**的记录仍在 |

## 三、Windows / Linux：隐藏数据与时间戳

| 攻方：怎么藏 | 守方：怎么查 |
|---|---|
| **ADS（NTFS 交换数据流）**：`type payload.bin > report.pdf:win32res.dll` —— **文件看起来正常，payload 在附属流里** | ① `dir /r`（**能列出 ADS**）；② `Get-Item -Stream *`（PowerShell）；③ **列目录时看文件大小、然后把 ADS 单独导出**：`Get-Content report.pdf -Stream win32res.dll -AsByteStream` |
| **改时间戳**（Timestomp）：`Set-ItemProperty` / `touch -r` | ① **`$STANDARD_INFORMATION` 与 `$FILE_NAME` 两个时间戳不一致**（改工具通常只改前者）——**这是最硬的判据**；② MFT 里 `$FILE_NAME` 时间**早于** `$STANDARD_INFORMATION` ⇒ 被改过；③ Linux：**`ctime` 改不了**（只能改 mtime/atime）⇒ `stat` 里 **mtime 新但 ctime 旧 = 被动过** |
| **文件名伪装**（把马命名为系统文件名） | ① 看**路径是否合理**（系统服务不在 `/usr/local`、`C:\Users\Public`、`%TEMP%`——**见 `应急响应总纲.md` §第二现场**）；② 比对文件哈希与发行版官方包（`dpkg -V` / `rpm -Va`） |
| **进程名伪装**（`svchost.exe` 放在非 System32） | `wmic process get ExecutablePath` / `Get-Process | Select Path`；**父进程异常**（svchost 的父进程应是 services.exe） |

## 四、Linux：日志与命令历史

| 攻方：怎么清 | 守方：怎么查 |
|---|---|
| `history -c` / 删 `.bash_history` | ① **`.bash_history` 文件不存在或大小为 0** = 被清；② **但 `history -c` 不清当前会话内存** ⇒ `cat /proc/<pid>/mem` 或 **`cat /proc/<pid>/environ`/`cmdline`** 拿运行中信息；③ **审计日志（auditd）里的 `execve` 记录不受影响** ⇒ `ausearch -m execve` |
| 删 `/var/log/*`（清空或 `> file`） | ① **文件 inode 未变但大小为 0** = 被 `>` 清空（**删掉重建的话 inode 会变**）⇒ 用 `ls -i` 对比；② 若进程仍持有句柄（rsyslog）⇒ **`ls -l /proc/<pid>/fd` 里能看到 `(deleted)` 的日志文件，仍可读**（★ 最硬的判据）；③ `journalctl` 的二进制日志独立于 `/var/log` ⇒ **`journalctl --since` 常能查到** |
| 改系统命令（替换 `ls`/`ps`/`ss` 藏后门**） | ① **`dpkg -V`（Debian）/ `rpm -Va | grep -E "5|T"`（CentOS）** 比对包完整性 —— **实测判据**；② 看文件 mtime 与包安装时间不符；③ 用**绝对路径 + 静态编译工具**（`busybox`）绕过被替换的命令 |
| `ld.so.preload` 劫持（`/etc/ld.so.preload` 指向恶意 .so） | **`cat /etc/ld.so.preload` 应为空或不存在** —— 有内容必可疑；`ldd /bin/ls` 看是否有非系统 .so |
| 加载内核模块 rootkit | `lsmod` 与 `/proc/modules` 对比；`/sys/module/*/sections` 找隐藏模块；**内核内存取证**（volatility 的 `linux_check_modules`） |

## 五、★ 内存留存：日志清了，内存里往往还有

| 攻方以为清了 | 守方实际还能查到 |
|---|---|
| 清了 `Security.evtx` | **内存里的 `Security.evtx` 常未被清**（volatility：`filescan` 找 `.evtx` → `dumpfiles` 导出，导出后**改后缀为 `.evtx`** 即可用事件查看器打开）——**实测有效** |
| 删了凭据文件 | `cmdscan` / `consoles`（**攻击者敲过的命令**）、`hashdump`（**内存里的 NTLM**，改密码前的旧 hash 可能还在） |
| 关了进程 | `netscan`（**已结束进程的连接记录**：RDP 跳板地址、C2 外连 IP） |
| 删了下载的工具 | `filescan` 能找到内存中缓存的 PE 文件（**连 mz 头都在**）；`strings` 扫内存镜像能捞出 URL/命令 |

**volatility 三件套（实测命令）**：
```bash
vol.py -f mem.raw windows.netscan     # 连接记录 → RDP 跳板 / C2 地址
vol.py -f mem.raw windows.cmdscan     # 控制台敲过的命令
vol.py -f mem.raw windows.filescan | grep -i "pass\|key\|flag\|.evtx\|.txt"
vol.py -f mem.raw windows.dumpfiles -Q <物理地址> -D ./out    # 导出指定文件
vol.py -f mem.raw windows.hashdump    # NTLM 哈希
```

## 六、应急排查"查不到证据"的七条出路（**卡住时按序走**）

```
① 换数据源：日志没了 ⇒ 查 MFT / USN / Prefetch / Amcache / SRUM（执行痕迹不依赖事件日志）
② 换载体  ：磁盘没了 ⇒ 查内存/页面文件/hiberfil（pagefile.sys 可能有历史痕迹）
③ 换网络  ：主机没了 ⇒ 查流量（pcap 里有全部交互）
④ 换旁证  ：本机没了 ⇒ 查同网段其它主机、域控（认证日志 4624/4648 记的是"谁从哪来"）
⑤ 换时间  ：具体事件没了 ⇒ 查"时间簇"（见 应急响应总纲 §时间簇判据）
⑥ 换对象  ：文件没了 ⇒ 查进程句柄（/proc/<pid>/fd 的 deleted、Windows 的 handle.exe）
⑦ 换方向  ：这些都排除 ⇒ 可能**根本没被清**，是**找错地方了**（见 应急响应总纲 §第二现场）
```

**★ 第 ⑦ 条最容易被忽略**：很多"痕迹被清了"其实是"**痕迹不在你以为的地方**"（Tomcat `work/` 的 jsp 源码、PHP 缓存马、`/tmp` 注入包）。

## 七、进攻侧视角（做攻防题/藏痕迹时看这列）

按"被发现概率从高到低"排列：

| 动作 | 风险 | 更稳的替代 |
|---|---|---|
| 清事件日志 | **极高**（1102 自证 + 内存留存） | 不清，只**避免产生**记录（用不落日志的执行方式） |
| ETW patch | 中（仅进程内有效，内存可查） | 用不依赖 ETW 的执行链 |
| 删文件 | 中（MFT 残留 + 可恢复） | **同目录改名**（时间戳合法）或 ADS 隐藏 |
| history -c | 低（但仍留有 inode 痕迹） | 不敲敏感命令（用 `export HISTFILE=/dev/null`） |
| ADS 藏 payload | 低（需 `dir /r` 才看得到） | 继续用 ADS（这是当前最实用的） |
| 时间戳伪造 | 低（需同时改两个时间戳才无缝） | 用**原文件的时间戳**覆盖（`touch -r` 参考合法文件） |
